System implementation note

MOM'S KID HOTEL

User identification, role authorization, 2FA, password protection, backups, and deployment | October 2026

Task and implementation summary

The requirement was to identify users, authorize actions by role, require two-factor authentication, protect passwords with hashing, salt, and pepper, create local and online backups, and deploy the system. MOM'S KID HOTEL implements these functions using a browser interface, a Node.js/Express API, SQLite, email verification, and encrypted backups. Render deployment configuration is prepared; publishing and live production verification remain to be completed.

1. System design and user identification

The application separates the presentation layer from security-sensitive decisions. HTML, CSS, and browser-side JavaScript provide the branded, responsive hotel login and dashboards. The Express server exposes JSON endpoints for registration, sign-in, code verification, recovery, account management, and backups. SQLite stores users, roles, sessions, challenges, and audit events. Email addresses are normalized before lookup; a case-insensitive unique constraint prevents duplicate accounts.

Customers may register, and registration always assigns the least-privileged customer role. Admins can provision managers, staff, and customers; managers can provision staff and customers. The first administrator is created through a setup command. This prevents public registration from granting elevated access. Independent secrets for password peppering, session-token hashing, and backup encryption are read from private environment settings, never client-side code or source control.

2. Password hashing, salt, and pepper

Passwords are never stored in plaintext. Each password must be 12–128 characters. The server applies HMAC-SHA-256 using a secret application pepper, then derives a 64-byte verifier with Node.js scrypt (N=32,768, r=8, p=1). Every account receives a fresh cryptographically random 16-byte salt stored alongside the verifier. The salt prevents equal passwords from having equal stored values; the pepper is a separate secret kept outside the database. Password verification uses a timing-safe comparison. The initial admin password is entered through a hidden terminal prompt and hashed before storage.

3. Sign-in and mandatory two-factor authentication

To sign in, a user selects the account type, enters the registered email and password, then submits the form. The selected role must match the role stored for that account. A correct password only starts verification: it does not create a logged-in session. The server emails a random six-digit code using the configured SMTP service. The user enters the code in the page; it expires after five minutes, is limited to five guesses, and can be used only once. The database stores keyed digests rather than the code itself. If email delivery is missing or fails, sign-in is denied, so there is no password-only fallback.

After successful verification, the server issues a random session token in an HttpOnly, SameSite=Strict cookie, marked Secure in production over HTTPS. Only a keyed digest of the token is stored. Sessions last 12 hours by default or up to 30 days when “Remember this device” is selected. Logging out invalidates the session; the next login requires a fresh email code. Role mismatch, wrong credentials, expired codes, and unauthorized API calls are rejected.

4. Role-based authorization

RolePrincipal permissions
adminView/manage accounts, create permitted roles, change roles, view audit events, and request backups. Admin accounts cannot be deleted; the last admin cannot be demoted.
managerView team/audit information and create staff or customer accounts; cannot assign elevated roles or request backups.
staffRead the customer directory; cannot manage accounts or use admin-only actions.
customerAccess their own profile and customer dashboard.

Role checks run in server-side middleware for every protected API request; hiding a button in the browser is not considered access control. Account changes are audit logged. Admin deletion permanently removes only non-admin accounts, revokes their sessions and pending challenges, and records the action. These controls protect information while giving each role its own dashboard and permitted actions.

5. Password recovery and backups

If a user forgets a password, select “Forgot your password?” and request a reset code at the registered email. The response does not reveal whether the email exists. The reset code expires after ten minutes and allows at most five attempts. A successful reset replaces the password hash and revokes that user’s sessions and pending codes; the user then signs in normally and completes 2FA. If the code does not arrive, verify the email address and ask the administrator to check SMTP configuration.

The backup service creates a consistent SQLite snapshot at startup and at a configured interval (24 hours by default). It encrypts each snapshot with AES-256-GCM, using a fresh random nonce and authentication tag, before saving it. Admins may also request a backup from the dashboard. When an S3-compatible bucket and credentials are configured, the encrypted file is uploaded as an online off-site copy. A local encrypted backup on Render's persistent disk is not an offline or air-gapped copy; a separate disconnected copy and periodic restore test are recommended. The backup key must be preserved securely.

6. Challenges and safeguards

Key challenges were ensuring incomplete SMTP cannot bypass 2FA, enforcing permissions at the API rather than relying on interface visibility, and ensuring account deletion also revokes outstanding access. Deployment required special care because SQLite needs persistent storage and a single service instance; an ephemeral host could lose user records. Railway must use a persistent volume mounted at /data. Application keys and SMTP credentials must be entered privately in the Railway service variables, never uploaded from .env.

The automated tests verify authentication and 2FA, registration, recovery, role boundaries, password hashing, schema migration, and backup encryption; all 11 passed during preparation of this note. The app runs locally; its Railway deployment is prepared but not yet complete. Remaining work is to upload the code with the Railway CLI while excluding .env, attach the persistent volume, enter production secrets, create the production administrator, generate a public HTTPS domain, and test login, email delivery, authorization, and backup restoration. Thus, application features are implemented, but the deployment requirement is not yet fulfilled until these steps are completed.
